# PC Monitor — модульная архитектура

## Цель

Каждая функциональная часть должна изменяться отдельно, собираться без ручного поиска по монолитному файлу и иметь собственный слой локализации и диагностики.

## Правила каталогов

- `Core/Monitoring/` — получение, нормализация и история сенсоров.
- `Core/Tiles/` — конфигурация, вычисление значения, история и стили плиток.
- `Core/Settings/` — схема настроек, миграции, чтение/запись и валидация.
- `Core/Localization/` — ключи, загрузка каталогов и форматирование локализованных значений.
- `Core/Diagnostics/` — единый журнал ошибок, проверка конфигурации и отчёты диагностики.
- `Core/Features/<FeatureName>/` — бизнес-логика отдельной вкладки или функции.
- `Views/Tabs/<FeatureName>/` — XAML и code-behind только для UI соответствующей вкладки.
- `Views/Dialogs/` — независимые диалоги.
- `Localization/` — только данные переводов; новые тексты не добавляются в C#.
- `tools/` — проверочные скрипты, не используемые приложением во время запуска.

## Контракты

Каждая вкладка должна иметь:

1. отдельный `View`;
2. отдельный `ViewModel` или feature-controller;
3. методы `Attach`, `ApplyLanguage`, `Dispose`;
4. события только для команд наружу (`StatusChanged`, `Request...`);
5. отсутствие прямого доступа к `MainWindow` и его полям.

Каждая плитка должна иметь:

1. `TileConfig` как сериализуемую модель;
2. `TileViewModel` для текущего значения и истории;
3. отдельный renderer/style без логики опроса;
4. ключ метрики и ключи локализации вместо жёстко зашитого текста;
5. проверку конфигурации при загрузке.

## Локализация

- Ключи и переводы хранятся в `Localization/*.json`.
- Все четыре файла должны иметь одинаковый набор ключей: `ru`, `en-GB`, `en-US`, `zh`.
- UI-код не должен содержать условные цепочки с текстами для языков.
- Динамические сообщения строятся из ключа и параметров.
- `tools/validate-localization.ps1` запускается перед сборкой.

## Настройки

- Изменение схемы повышает `SettingsSchemaVersion`.
- Каждое изменение схемы получает отдельную миграцию.
- `Normalize()` только вызывает миграции и валидаторы, а не содержит бизнес-логику вкладок.
- Плитки, OSD, тесты и интерфейс должны иметь отдельные секции настроек.

## Диагностика

Ошибки должны сохранять:

- компонент;
- операцию;
- исключение;
- время;
- безопасное сообщение для пользователя.

Пустые `catch` разрешены только для необязательных операций UI и должны иметь комментарий о причине. Ошибки опроса сенсоров, записи настроек и запуска тестов должны попадать в общий журнал.

## План миграции

1. Внешняя локализация и автоматическая проверка четырёх каталогов.
2. Разделение `MainWindow` на контроллеры навигации, языка, трея и мониторинга.
3. Выделение `SettingsStore`, миграций и валидаторов.
4. Выделение Tiles feature: конфигурация, каталог метрик, редактор и renderers.
5. Выделение каждой вкладки в feature-папку с единым контрактом.
6. Удаление старых дублей (`DashboardView` и мёртвых путей) после проверки ссылок.
7. Полная сборка, запуск, smoke-тесты и проверка четырёх языков.
